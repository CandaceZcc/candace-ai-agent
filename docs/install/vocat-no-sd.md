# VoCat No-SD Plan

本页描述在 **暂时没有 microSD 卡** 的前提下，如何先把 VoCat 跑成一个可用的语音终端，并接入当前仓库的 QQ / 本机能力链路。

## 目标

优先完成最小闭环，而不是先追求完整 GUI：

- VoCat 能启动、联网、收音、播音
- 语音请求能进入本机 `qq-ai-bridge`
- 本机可以读取仓库和 OpenClaw 文档
- 本机可以调用已有功能，并把结果：
  - 回传给 VoCat 语音播报
  - 同步发到 QQ
- VoCat 可以切换表情

## 当前判断

基于当前串口日志，设备现在运行的是 `VolcRTCDemo`，不是官方出厂 GUI 固件。

已确认：

- 音频输入芯片 `ES7210` 初始化成功
- 音频输出芯片 `ES8311` 初始化成功
- LCD 和触摸初始化成功
- `fs_sdcard` 挂载失败，错误为 `sdmmc_card_init failed (0x107)`

这说明：

- 没插卡时，板子并不是完全没启动
- 但 SD 卡失败会把整套板级初始化拖入不稳定状态
- 语音和显示本身未必依赖 SD 卡

## 已做修改

已在设备端源码里把板级初始化改成：

- 必须初始化：`audio_dac`、`audio_adc`、`display_lcd`、`lcd_brightness`
- 可选初始化：`fs_sdcard`

文件：

- `/home/cancade/ConversationalAI-Embedded-Kit-2.0/application/platform/src/espressif/basic_board.c`

这一步的目的，是让设备在没有 SD 卡时尽量继续完成音频和显示初始化，不再把 `fs_sdcard` 当成硬前提。

## 推荐架构

采用“设备做终端，本机做大脑”的结构。

### 设备侧职责

- 麦克风采集
- 唤醒和基础交互
- 文本播报
- 表情显示
- 把请求发送到本机服务

### 本机侧职责

- `qq-ai-bridge` 做总入口
- 读取仓库和 OpenClaw 文档
- 调用本机已有 agent / 自动化功能
- 发 QQ 消息
- 决定设备播报内容和表情内容

## 最小闭环

最短目标是：

1. VoCat 收音
2. 请求进入 `/vocat/webhook`
3. `vocat_service.py` 分流请求
4. 本机返回结果
5. 同时执行：
   - 设备播报
   - QQ 发消息
   - 表情控制

## 分阶段执行

### 阶段 1：确认无卡可启动

- 重新编译并烧录修改后的 `VolcRTCDemo`
- 观察串口日志
- 目标不是让 `fs_sdcard` 成功，而是确认：
  - 不再因为 `fs_sdcard` 失败导致整体不可用
  - LCD 正常显示
  - 语音采集链路能继续启动

### 阶段 2：打通设备到本机

- 让设备连上 Wi-Fi
- 让设备把语音请求送到本机 webhook
- 优先验证最小请求：
  - 固定文本
  - 固定播报
  - 固定表情

### 阶段 3：打通本机到 QQ

- 使用现有 `NapCat + qq-ai-bridge`
- 保持“个人 QQ”链路，不切到官方 QQ Bot
- 设备请求经本机处理后：
  - VoCat 播报
  - QQ 同步收到文本

### 阶段 4：挂接本机能力

- 读取仓库内 Markdown
- 接入 OpenClaw / OCAI 本地命令
- 接入 PC agent
- 对外暴露为 VoCat 可触发的技能

## 为什么现在不切 ESP-Claw

`ESP-Claw` 很值得参考，但当前不是最快落地路线：

- 官方现成支持板里没有 `ESP-VoCat`
- 需要额外做板级适配
- 自带 QQ 能力走的是官方 QQ Bot，不是当前项目的 `NapCat + 个人 QQ`

更合适的定位是：

- 现在先用现有仓库打通 VoCat 终端链路
- 以后再把 `ESP-Claw` 作为设备端架构升级方向

## 当前优先级

当前优先顺序应当是：

1. 无 SD 卡容错启动
2. 设备联网
3. 设备到本机 webhook
4. 本机到 QQ
5. 读文档和调用本机功能
6. 语音播报和表情联动

## 风险

- 没有 SD 卡时，某些资源型功能仍可能不可用
- 如果 `VolcRTCDemo` 内部还有其它流程隐式依赖 `/sdcard`，后续仍可能需要继续补丁
- 即使无卡可运行，长期稳定性仍不如插卡方案

## 建议

即使当前按无卡方案推进，后续仍建议准备一张 microSD 卡。

原因不是“没卡就完全不能做”，而是：

- 更容易规避板级资源依赖
- 更容易保住缓存、资源文件、持久化状态
- 后续扩展能力时阻力更小
