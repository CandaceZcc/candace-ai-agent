# 个性化校园邮件推送设计

**状态：** 设计已批准
**日期：** 2026-07-21
**范围：** 仅限所有者使用的只读校园邮件分类与 QQ 推送

## 背景

Phase A 当前已经完成邮件功能的安全基础：

- 支持按日期范围查询的所有者私聊 QQ 命令；
- 通过 TLS 只读访问 IMAP；
- 有边界限制的 MIME 解析和本地私有归档；
- 使用 `gpt-5.6-terra` 生成不调用工具的摘要；
- 通过 NapCat 向 QQ 发送结果；
- 按需邮件功能有独立开关。

目前还没有个性化过滤、逐封相关度判断、新邮件监测、反馈学习和高价值邮件自动推送。原计划中尚未实现的调度器只覆盖固定时间的日报和周报，本设计将取代该方案。

## 目标

1. 在不修改邮箱状态的前提下，通常在新邮件到达后约 5 分钟内完成检测。
2. 过滤明确无关的例行邮件。
3. 综合确定性规则、模型判断和用户反馈，识别与用户相关的高价值邮件。
4. 将高度相关且紧急的邮件立即通过 QQ 推送给用户。
5. 每天 12:30 和 20:30 推送增量摘要，涵盖最近 24 小时内相关但不紧急的邮件，并避免重复。
6. QQ 只接收模型提炼后的摘要，不接收原始邮件正文。
7. 每条推送都显示相关度和紧急性。
8. 支持通过 QQ 明确反馈进行学习，同时保持规则可查看、可解释、可手动修改。
9. 凭据、私人邮件、学习得到的偏好、处理状态和运行日志不得进入 Git。

## 不在本期范围内

- 发送邮件或提供任何 SMTP 能力。
- 标记已读、移动、删除邮件或修改服务端状态。
- 自动回复邮件。
- 默认将所有学校通知视为有价值。
- 默认推送泛招聘、实习或普通校园活动通知。
- 在邮件流程中调用图片生成 API。
- 替换 `邮件 今天`、`邮件 本周` 等手动命令。
- 自动发送周报。手动查询本周和上周仍然保留。

## 用户相关性画像

初始画像包含以下正向信号：

- 人与人之间的直接回复，无论使用学校域名还是外部域名；
- 明确发给用户本人，而不是只发给大型邮件列表；
- 计算机科学、计算、计算机系、CST；
- Year 3、third year、2024 cohort、大三、2024级；
- AI、机器学习、大语言模型、软件工程、Web、App、数据科学、数据库、网络安全、系统、云计算、操作系统、算法和编程竞赛；
- 机器人、嵌入式系统、物联网、自动化和软硬件结合项目；
- 与专业相关的科研、学术竞赛和技术活动；
- 考试、课程调整、截止日期、要求确认、提交、缴费、出席和账号安全。

初始画像包含以下负向信号：

- 泛招聘、普通校招和批量实习推广；
- 普通商业推广或营销邮件；
- 与个人、年级、院系和技术方向都无关的例行校园活动通知；
- 用户已经明确拒绝过的重复群发通知。

招聘或实习邮件只有在明确匹配用户专业、年级或技术兴趣时，才可能被判定为相关。来自学校理工学部或计算机系的邮件始终可以进入语义判断，但不能仅凭学校域名直接触发即时推送。

教师个人邮件和学校机构邮件通常使用同一个学校域名，因此自动评分不能仅凭域名或显示名称推断发件人是教师还是机构。默认区分依据是回复线程标记、课程/考试/行动词、收件范围和正文语义。只有用户手动配置或明确反馈后，发件人和域名权重才参与评分。

## 系统架构

自动化流程由七个边界清晰的组件组成：

1. `EmailMonitor`：通过只读 IMAP 轮询新 UID。
2. `EmailProcessingStore`：保存游标和逐封邮件的处理状态。
3. `EmailPreferenceStore`：加载手动规则和反馈学习结果。
4. `EmailRuleClassifier`：应用可解释的正向、负向规则。
5. `EmailSemanticClassifier`：调用无工具模型，生成结构化判断。
6. `EmailDeliveryPlanner`：将结果分配到即时推送、摘要队列或静默忽略。
7. `EmailFeedbackService`：解析 QQ 本地编号并更新学习偏好。

现有 MIME 解析器、归档服务、Agent runtime、NapCat 客户端和 QQ skill 路由继续作为实现基础。

### 处理流程

```text
每 5 分钟触发一次
  -> 只读 UID 查询
  -> 持久化新发现的邮件身份
  -> 有边界的 MIME 解析和归档
  -> 确定性规则评分
  -> 检查用户明确设置的硬忽略规则
  -> 对符合条件的候选邮件执行无工具语义分类
  -> 持久化结构化判断
  -> 即时 QQ 推送 / 等待摘要 / 静默忽略
  -> 仅在 NapCat 发送成功后标记为已送达
```

学校院系邮件、私人直接回复，以及带有个人正向信号但判断不明确的邮件，都必须进入语义分类。只有用户明确设置了硬忽略规则，或者确定性规则同时满足“强负向信号”和“没有任何正向信号”，才允许跳过模型调用。

## 只读新邮件监测

监测器默认每 300 秒运行一次。它使用 IMAP UID 命令，并持久化以下数据：

- 邮箱文件夹名称；
- `UIDVALIDITY`；
- 已可靠记录的最后一个 UID；
- Message-ID 的哈希，用于跨会话去重。

只有在对应处理记录已经原子写入后，游标才能前移。如果一次轮询发现的邮件超过单轮上限，应分成多个有界批次继续处理。

当 `UIDVALIDITY` 变化时，监测器重新建立 UID 游标，并结合 Message-ID 哈希和近期处理记录防止重复推送。IMAP 始终使用 `readonly=True` 选择邮箱；禁止使用 `STORE`、`COPY`、`MOVE`、`EXPUNGE`，也不允许出现任何 SMTP 操作。

## 偏好存储与反馈学习

私人偏好数据存放在：

```text
~/.candace/email-agent/profile.json
~/.candace/email-agent/learned-feedback.json
```

文件采用原子替换写入，权限为 `0600`，并且位于仓库之外。手动编辑的画像优先于自动学习结果。手动配置无效时，不替换内存中最后一份有效画像；系统只向用户发送一次去重后的 QQ 配置提醒。

画像支持：

- 关注和忽略的发件人；
- 关注和忽略的域名；
- 正向和负向短语；
- 兴趣类别及其别名；
- 年级和入学年份别名；
- 仅能由用户明确操作创建的硬忽略规则；
- 分数调整项；
- 单调递增的画像版本号。

正面和负面反馈可以在限定范围内调整发件人、域名、类别和语义信号的权重。用户没有回复 QQ，不能被视为负面反馈。所有学习规则都必须可以查看和撤销。

画像版本变化后，系统可以重新评估最近 7 天内被忽略的邮件，但不能超出 30 天归档保留期。重新评估不得重复推送已经送达的邮件。

## 确定性规则分类

规则分类器输出初始分数、命中的信号，以及下列三种资格结果之一：

- `semantic_required`：需要模型语义判断；
- `explicit_hard_ignore`：命中用户明确设置的硬忽略规则；
- `deterministic_low_value`：可由确定性规则判定为低价值。

私人直接回复、明确发给用户本人、年级关键词、课程行动要求和技术兴趣匹配会提高分数。普通群发特征、泛活动通知和泛招聘会降低分数。普通负向信号不得覆盖私人行动要求、考试调整、账号安全事件或用户明确设置的正向规则。

只有用户明确设置的硬忽略规则可以完全跳过语义分析。`deterministic_low_value` 必须同时满足两个条件：存在强负向证据，并且没有用户正向信号。

收件范围较广、邮件列表标记或群发头只能作为弱信号。学校群发邮件仍需进入语义分类，除非主题或内容同时出现泛招聘、例行活动等强低价值信号。

## 模型分类

符合条件的候选邮件按有界批次交给 `gpt-5.6-terra` 分类，并设置 `reasoning_effort=high`。请求沿用现有 `email_summary` 等级的安全边界：

- `tools=[]`；
- 不启用托管搜索；
- 不启用本地工具；
- 不允许回退到旧聊天路径；
- 仅发送经过清洗和长度限制的内容；
- 明确隔离邮件中的提示注入。

模型为每个本地邮件编号返回严格的结构化结果：

```json
{
  "alias": "E-1042",
  "relevance_score": 92,
  "urgency": "high",
  "category": "course_change",
  "concise_title": "课程考试安排调整",
  "summary": "考试时间和教室发生变化。",
  "action": "今晚前确认新安排。",
  "deadline": "2026-07-22T20:00:00+08:00",
  "reason": "与你当前年级课程直接相关",
  "confidence": 0.94
}
```

`urgency` 只允许使用 `low`、`medium`、`high`、`critical`。无法确定截止时间时必须返回 `null`，模型不得编造时间。原始主题已经简短准确时可以保留，否则由模型生成精简标题。

模型输出如果格式错误、字段不完整或尝试调用工具，系统必须拒绝该结果，不能将它转换为原始或半可信的 QQ 消息。

## 路由策略

默认路由矩阵如下：

| 相关度 | 附加条件 | 处理方式 |
| --- | --- | --- |
| 80–100 | 紧急性为高或紧急 | 立即 QQ 推送 |
| 60–100 | 不需要立即处理 | 进入下一次增量摘要 |
| 40–59 | 存在强个人或技术信号 | 进入摘要中的“可能相关”位置 |
| 40–59 | 没有强正向信号 | 静默忽略，保留供反馈复查 |
| 0–39 | 没有覆盖规则 | 静默忽略 |

截止时间在 48 小时内、明确要求回复、考试或课程调整、账号安全事件，以及可能造成经济或学业损失的内容，都可以提高紧急性。相关度和紧急性必须分开判断，避免一封普遍重要但与用户没有直接关系的校园通知造成即时打扰。

## QQ 推送格式

即时消息不包含原始正文，也不直接显示冗长的原始主题：

```text
[相关度 92 | 紧急性 高]
课程考试安排调整

核心：考试时间和教室发生变化。
行动：请在今晚前确认新安排。
截止：7月22日 20:00
来源：发件人名称
编号：E-1042
```

来源保留发件人显示名称。较长主题由模型压缩；主题本身已经简短准确时可以原样保留。签名、历史引用、跟踪内容、长链接和原始正文不得发送到 QQ。

## 增量摘要

摘要任务按照配置的本地时区，在每天 12:30 和 20:30 运行。每次回看最近 24 小时，但只包含尚未通过即时推送或此前成功摘要送达的相关邮件。

每次摘要最多包含：

- 3 条“需要行动”；
- 4 条“值得关注”；
- 1 条“可能相关”。

没有新内容时不发送空摘要。相似的低价值通知应合并或省略。系统可以用一句话说明已忽略若干普通通知，但不得逐条列出或复述内容。

定时摘要优先使用已经持久化的短分类结果进行组合。只有确实需要跨邮件归并时，才再次调用模型。这样可以控制 API 用量，也能避免同一正文被重复发送给模型。

## 发送幂等性

每封邮件分别记录分析状态、即时推送状态、摘要资格、摘要送达状态和反馈状态。只有 NapCat 返回 HTTP 成功且 `retcode=0` 后，才能写入最终送达状态。

即时推送和摘要推送使用由邮件身份及路由生成的幂等令牌。每次摘要任务还使用独立的时段令牌，例如：

```text
email_digest:2026-07-21T12:30+08:00
email_digest:2026-07-21T20:30+08:00
```

发送失败的项目保持待发送状态，并按照有上限的退避策略重试。bridge 重启、轮询重叠或调度补跑都不能产生重复 QQ 消息。定时摘要补跑只处理最近 24 小时内仍未送达的相关邮件。

## 反馈命令

所有者私聊的 `EmailSkill` 新增以下命令：

```text
邮件 E-1042 有用
邮件 E-1042 忽略
邮件 E-1042 忽略此类
邮件 E-1042 关注发件人
邮件 E-1042 撤销反馈
邮件 偏好
```

编号只在本地使用，不暴露 IMAP UID 或 Message-ID。非所有者或群聊中的反馈命令必须被拒绝。

`忽略此类` 先生成一条可查看、可撤销的学习规则，不能在后台悄悄创建范围不受控制的永久黑名单。`邮件 偏好` 返回不含凭据的精简规则摘要。手动修改配置并通过校验后，无需重启 bridge 即可生效。

## API 使用方案

- QuotaRouter 的 `gpt-5.6-terra` 使用高推理强度，负责邮件语义分类和必要的跨邮件压缩。
- 每轮新增候选邮件按批次处理，同一份结构化结果同时用于路由和生成 QQ 文本。
- DeepSeek V4 继续用于普通聊天，默认不接触邮件内容。
- Banana 只用于图片功能，邮件路径无法调用它。
- Provider API Key 和 IMAP 凭据只保存在权限为 `0600` 的外部环境变量文件中。

系统只记录汇总后的 token 用量、耗时、状态、路由和工具调用次数，不记录内容。每次模型请求之前，都必须限制邮件数量和清洗后文本总长度。

## 配置与回滚

新的自动化功能使用相互独立且默认关闭的开关：

```dotenv
EMAIL_AGENT_ENABLED=false
EMAIL_MONITOR_ENABLED=false
EMAIL_IMMEDIATE_PUSH_ENABLED=false
EMAIL_DIGEST_PUSH_ENABLED=false
EMAIL_SHADOW_MODE=true
EMAIL_POLL_INTERVAL_SECONDS=300
EMAIL_DIGEST_TIMES=12:30,20:30
```

`EMAIL_AGENT_ENABLED` 继续控制所有者手动邮件命令。三个新增开关分别控制监测、即时推送和定时摘要。观察模式允许轮询和分类，但禁止发送邮件内容。

尚未上线的 `EMAIL_DAILY_DIGEST_*` 和 `EMAIL_WEEKLY_DIGEST_*` 方案由本设计取代。手动查询今天、本周和上周等命令保持不变。

## 隐私与日志

所有私人运行文件必须位于仓库之外，或者放在现有 Git 忽略的数据目录中。真实邮件、发件人、地址、凭据、学习偏好、状态文件、trace 和附件都不得提交。

启用自动化之前，当前 NapCat 出站日志必须停止记录邮件推送的消息预览。邮件日志只能包含：

- 本地编号或不可逆哈希；
- 规则和模型分数；
- 类别与路由；
- 处理耗时和汇总 token 数；
- 工具调用次数；
- 脱敏后的发送状态。

云端模型必然会处理经过限制的候选邮件内容，运维文档必须明确说明这一点。清洗后的原始归档沿用默认 30 天保留期，并由有边界的清理任务删除。本阶段不上传或总结附件。

## 异常处理

- **模型不可用：** 候选邮件保持待分析状态并重试，不能发送原文。
- **模型不可用时发现疑似紧急邮件：** 只发送一次去重且不含邮件内容的运行提醒，并继续重试。
- **模型结果无效：** 拒绝结果，记录安全错误码，并在限定策略内重试。
- **IMAP 故障：** 保留原游标；故障持续超过阈值后只发送一次去重提醒，恢复后再通知一次。
- **NapCat 故障：** 不标记发送完成；重试时不能重复已经成功的分段。
- **画像无效：** 继续使用最后一份有效画像，并只提醒一次。
- **队列积压：** 优先处理最新的紧急候选，其余项目保留可靠状态，后续分批处理。

## 验证方案

专项测试必须覆盖：

- UID 轮询、游标持久化、`UIDVALIDITY` 变化和只读约束；
- 规则优先级、硬忽略限制和正向信号覆盖；
- 结构化模型结果解析、错误输出和零工具约束；
- 所有路由阈值及截止时间边界；
- 即时推送成功、部分失败、重试和重启幂等性；
- 12:30、20:30 增量窗口和 8 项上限；
- 空摘要和重复摘要抑制；
- 反馈权限、学习、撤销和手动画像优先级；
- 无效画像重新加载；
- QQ、日志、trace、指标和 Git 中均不存在原始邮件内容；
- Provider、IMAP、NapCat 故障与恢复；
- 各回滚开关相互独立。

真实环境测试之前，仍需通过仓库完整测试、Ruff、编译检查、diff 检查和已跟踪文件敏感信息扫描。

## 分阶段上线

1. 完成实现和验证，保持所有自动化开关关闭。
2. 在观察模式下启用监测 24 小时，只生成本地脱敏判断报告，不自动推送。
3. 检查误报和漏报，调整初始画像。
4. 启用即时推送，暂时保持定时摘要关闭。
5. 启用 12:30 和 20:30 增量摘要。
6. 验证重启幂等性，并将实际 API 用量与 Provider 账单对照。
7. 保留独立关闭监测、即时推送或摘要推送的能力，且不影响普通 QQ 聊天。

## 验收标准

- 新邮件通常能在 5 分钟内完成评估。
- 高度相关且紧急的邮件只通过 QQ 推送一次。
- 相关但不紧急的邮件只在下一次符合条件的摘要中出现一次。
- 明确无关的邮件不会产生 QQ 条目。
- 推送内容包含相关度、紧急性、精简标题、提炼内容、发件人显示名称和本地反馈编号，但不包含原始正文。
- 用户反馈能改变后续判断，并且可以撤销或被手动配置覆盖。
- bridge 重启和重复轮询不会导致重复推送。
- 模型运行不暴露任何工具，也不允许回退到旧聊天路径。
- IMAP 始终只读，不存在 SMTP 或任何邮件修改能力。
- 日志和 Git 中没有凭据、发件人地址、真实邮件内容或学习得到的私人偏好。
